01 / architecture

Architecture et code

Pile technologique, organisation du dépôt, modèle de données et cycle de vie d’un colis.

siaoctawacta/Tracking · branche main

1.1Vue d’ensemble

L’application est découplée : une application monopage (SPA) React servie comme fichiers statiques, et une API REST JSON sans état en Node.js, sous /api/v1. L’API ne génère aucun HTML ; la SPA ne contient aucune logique métier (prix, numéros de suivi, transitions de statut et droits sont décidés par l’API). En production, un seul déploiement Vercel sert le site (fichiers statiques sur le CDN) et l’API (une fonction serverless) sur la même adresse ; les données sont chez Supabase (PostgreSQL et stockage des photos).

1.5Cycle de vie d’un colis et droits

Statuts ordonnés : REGISTERED → LOADING → IN_TRANSIT → ARRIVED → READY → DELIVERED. Chaque changement crée un ShipmentEvent et, s’il fait avancer le colis, une alerte WhatsApp pour l’étape.

RôleStatuts autorisésRègle
AGENT_GZREGISTERED, LOADING, IN_TRANSITUniquement vers l’avant (sinon 409 status_backwards)
AGENT_LOMEARRIVED, READY, DELIVERED
ADMINTousPeut corriger en arrière : aucune alerte n’est alors envoyée
CLIENTAucunLecture de ses propres colis uniquement

Numéro de suivi : KC-AAAA-XXXXXX, 6 caractères tirés par générateur cryptographique dans un alphabet de 32 signes sans 0/O ni 1/I (plus d’un milliard de combinaisons). Prix calculé par l’API : aérien au kg, maritime au m³, minimum de facturation (server/src/lib/domain.ts).

2.4Conventions

  • Toute modification du modèle passe par une migration (db:migrate) versionnée dans server/prisma/migrations/. Après une migration, régénérer le client : npx prisma generate (fait automatiquement par npm install).
  • Chaque entrée de l’API est décrite par un schéma zod .strict() : un champ inconnu est refusé (400 validation_error).
  • Les erreurs métier passent par HttpError(statut, message, code) ; les messages sont en français, destinés à l’utilisateur.
  • Les coordonnées affichées sont dans web/src/lib/site.ts, celles des messages et PDF dans server/src/lib/company.ts, les tarifs dans server/src/lib/domain.ts.

04 / sécurité

Sécurité de l’application

Mots de passe, sessions, codes de vérification, contrôle d’accès, entrées, fichiers, en-têtes et limites connues.

OWASP Top 10

4.1Mots de passe

  • Hachage Argon2id (m=65536 Kio, t=3, p=1, sortie 32 octets) avec un sel aléatoire de 16 octets par hachage ; jamais stockés ni journalisés en clair.
  • Vérification à temps quasi constant : si l’utilisateur n’existe pas, un hachage factice est vérifié quand même ; le message d’erreur est identique (invalid_credentials).
  • Longueur minimale 10 caractères ; formulaires en type="password" avec autocomplete approprié.

4.2Sessions

ÉlémentMise en œuvre
Jeton d’accèsJWT HS256, 15 minutes, émetteur kader-cargo, audience kader-cargo-web, identifiant unique (jti) ; contient sub, role, name. L’API est sans état : chaque requête est authentifiée par ce jeton.
Refresh token32 octets aléatoires, 7 jours, stocké uniquement haché (SHA-256). Rotation à chaque usage ; un jeton déjà utilisé et rejoué révoque toute sa famille (détection de vol).
Cookies__Host-jwt, __Host-rt, __Host-csrf : HttpOnly; Secure; SameSite=Strict; Path=/, sans domaine. Inaccessibles au JavaScript (pas de localStorage).
Fin de sessionDéconnexion, désactivation ou refus d’un compte : révocation des refresh tokens en base.
SecretJWT_SECRET obligatoire en production (≥ 32 caractères) : l’API refuse de démarrer sinon.

4.3Protection CSRF et CORS

En plus de SameSite=Strict, toute requête qui modifie des données doit présenter dans l’en-tête X-CSRF-Token la même valeur que le cookie __Host-csrf (comparaison à temps constant). Le jeton est donné dans le corps de GET /auth/csrf, ce qui fonctionne aussi si le site et l’API sont sur des origines différentes. CORS n’est activé que si CORS_ORIGINS est renseigné (origines explicites, credentials, méthodes GET/POST/PATCH/DELETE).

4.4Codes de vérification et inscription

  • 6 chiffres tirés par crypto.randomInt. Seul un HMAC-SHA256 (clé : JWT_SECRET, message : destinataire + code) est stocké.
  • Validité 10 minutes, 5 essais puis verrouillage ; 60 s entre deux envois, 5 codes par heure et par destinataire ; un nouveau code invalide le précédent ; consommation atomique (un code ne sert qu’une fois).
  • Pas d’énumération des clients : une inscription sur un numéro existant envoie un code de connexion et répond exactement comme une nouvelle inscription ; une demande de code pour un compte inconnu répond pareil sans rien envoyer.
  • Un téléphone ou un e-mail n’est enregistré sur un compte qu’après preuve (code, Google, ou création par le personnel), car il donne accès aux colis enregistrés à ce numéro.
  • Comptes auto-inscrits en PENDING : aucune session possible (mot de passe, code, Google, refresh) avant validation par un administrateur.

4.5Connexion Google

Le jeton d’identité Google est vérifié par l’API (bibliothèque jose) : signature contre les clés publiques de Google, audience = GOOGLE_CLIENT_ID, émetteur accounts.google.com, expiration. Un compte existant n’est lié automatiquement que si Google certifie l’adresse (email_verified).

4.6Contrôle d’accès

  • Par rôle sur chaque route (middleware requireRole) et par statut (tableau 1.5).
  • Par objet : un client n’accède qu’aux colis dont le téléphone ou l’e-mail correspond à son compte ; sinon l’API répond 404 (et non 403) pour ne pas révéler l’existence du colis.
  • Le site masque les boutons non autorisés, mais l’API reste la seule autorité.
  • Suivi public : nom réduit (« Afi M. »), téléphone masqué (« +228 •• •• 33 ») ; 30 requêtes par minute et par IP contre l’énumération des numéros.

4.7Entrées, fichiers et erreurs

  • Injection SQL : uniquement des requêtes Prisma paramétrées, aucune requête SQL construite à la main.
  • Validation : schémas zod .strict() sur tous les corps et paramètres ; JSON limité à 100 Ko.
  • Photos : redimensionnées (1600 px) et recompressées en JPEG dans le navigateur, envoyées une par requête (limite de 4,5 Mo par requête sur Vercel) ; côté API, JPEG / PNG / WebP uniquement, vérifiés par signature binaire, 5 Mo maximum, nom aléatoire (UUID). Stockées dans un bucket Supabase privé (ou sur disque en droits 600) et servies uniquement par l’API après contrôle d’accès, avec X-Content-Type-Options: nosniff. La clé service_role ne quitte jamais le serveur.
  • XSS : React échappe tout le contenu ; aucune insertion de HTML brut ; CSP stricte sur le site.
  • Erreurs : aucune trace technique renvoyée au client (détails seulement dans le journal).

4.8En-têtes HTTP

RéponseEn-têtes
API (helmet)Content-Security-Policy: default-src 'none'; frame-ancestors 'none', Strict-Transport-Security (2 ans, preload), X-Frame-Options: DENY, Referrer-Policy: no-referrer, Cross-Origin-Resource-Policy: same-site, pas de X-Powered-By.

4.9Limitation de débit

RoutesLimite (par adresse IP)
POST /auth/login5 par 15 minutes (LOGIN_RATE_LIMIT)
Inscription, codes, Google60 par 15 minutes (beaucoup de clients mobiles partagent une même IP d’opérateur) + limites par destinataire (4.4)
GET /tracking/…30 par minute

Les compteurs sont stockés dans PostgreSQL (table RateLimit, une mise à jour atomique par requête) : la limite vaut pour l’ensemble des instances de la fonction Vercel, pas instance par instance. TRUST_PROXY=1 (Vercel ou Caddy) est indispensable pour que l’IP réelle du client soit utilisée.

4.10Limites connues et recommandations

  • Connexion à la base : chiffrée (SSL) vers Supabase ; le certificat n’est vérifié que si DATABASE_SSL=verify et DATABASE_CA_CERT (certificat CA de Supabase, téléchargeable dans les réglages de la base) sont renseignés — recommandé.
  • Sans WhatsApp ni SMTP configurés, les codes sont écrits dans le journal du serveur (mode « simulé ») : configurer les fournisseurs avant d’ouvrir les inscriptions.
  • Pas de double authentification pour le personnel : recommandé si l’équipe grandit (un code par e-mail à chaque connexion, par exemple).
  • Les codes, jetons et compteurs expirés sont purgés chaque jour par la tâche de maintenance (/cron/maintenance).
  • Les notifications du back-office sont lues par interrogation toutes les 10 secondes (simple et compatible avec une API sans état).

Intégrations

Supabase, WhatsApp, e-mail et connexion Google : fonctionnement et configuration.

supabase · twilio · meta · smtp · google

5.1WhatsApp

Code : server/src/lib/whatsapp.ts. Fournisseur choisi par WHATSAPP_PROVIDER ou détecté selon les identifiants présents ; sans identifiants : mode simulé.

  • Alertes d’étape : un message par étape franchie vers l’avant (y compris en masse), au plus un par étape et par colis. Envoi après la réponse HTTP (waitUntil sur Vercel), 3 tentatives (immédiate, +5 s, +20 s sur Vercel ; +30 s, +2 min sur un serveur) ; après le dernier échec, notification WHATSAPP_FAILED aux administrateurs. Une alerte restée en attente plus de 10 minutes est relancée par la tâche de maintenance quotidienne.
  • Codes et avis de compte : envoi immédiat (la réponse HTTP attend le résultat).
  • Meta : modèles approuvés nommés {META_TEMPLATE_PREFIX}{étape}, variables du corps {{1}} prénom, {{2}} numéro de suivi, {{3}} détail ; le modèle kader_otp (catégorie Authentification) porte aussi le code dans son bouton « Copier ».
  • Twilio : texte libre, ou modèles Content si TWILIO_CONTENT_SIDS associe une étape à un identifiant HX….

kader_otpAuthentificationCode de vérification

Les textes à soumettre à Meta ou Twilio sont dans docs/whatsapp-alertes.md.

5.2E-mail

Code : server/src/lib/mailer.ts (nodemailer, SMTP). Avec Gmail : validation en deux étapes, puis un mot de passe d’application dans SMTP_PASS, SMTP_HOST=smtp.gmail.com, port 465 sécurisé. Gmail limite le volume quotidien ; pour un volume plus important, utiliser un service d’envoi dédié (mêmes variables SMTP). Les e-mails sont envoyés en texte et en HTML aux couleurs de Kader Cargo.

5.3Connexion Google

  1. console.cloud.google.com : créer un projet, configurer l’écran de consentement OAuth (nom, logo, e-mail d’assistance).
  2. Identifiants → ID client OAuth, type « Application Web », origine JavaScript autorisée : https://kadercargo.com.
  3. Renseigner GOOGLE_CLIENT_ID et redémarrer l’API. Le site le récupère via GET /auth/options : aucune reconstruction du site n’est nécessaire.

5.4Supabase

  • Base PostgreSQL : l’API se connecte via le pooler de Supabase. DATABASE_URL = « Transaction pooler » (port 6543, adapté aux fonctions serverless) ; DIRECT_URL = « Session pooler » (port 5432), utilisé par les migrations Prisma. Chaque instance garde au plus 2 connexions (DB_POOL_MAX).
  • Storage : bucket privé photos ; l’API y écrit et lit avec la clé service_role (ou une clé secrète sb_secret_…) via l’API REST de Storage (server/src/lib/storage.ts). Le navigateur n’accède jamais directement au bucket.
  • Aucune autre fonctionnalité Supabase n’est utilisée (pas d’Auth Supabase, pas d’accès direct à la base depuis le navigateur) : l’authentification et les droits restent ceux de l’API.
  • Row Level Security : Supabase publie le schéma public par son API REST avec la clé publique anon. La migration enable_rls active la RLS sur les 11 tables, sans aucune politique : ces accès ne renvoient rien. L’API se connecte en tant que propriétaire des tables, qui n’est pas soumis à la RLS. Toute nouvelle table doit recevoir la même instruction dans sa migration.

6.4Premier administrateur

Depuis un ordinateur disposant du dépôt à jour et de Node.js 22, avec la chaîne Session pooler. La chaîne est saisie sans affichage, pour que le mot de passe de la base n’apparaisse ni à l’écran ni dans l’historique du terminal :

  Mot de passe (10 caractères min.) :     ← saisi sans affichage
$ unset DATABASE_URL

Le script affiche la base visée avant toute écriture : si la ligne indique « base locale », DATABASE_URL n’est pas définie dans ce terminal ; répondez N.

Jamais « npm run setup » ni « db:seed » sur la base Supabase

6.5Fonctionnement du build

  • vercel.json installe web/ et server/ puis lance server/scripts/vercel-build.mjs, qui produit .vercel/output (Build Output API) : le site dans static/, l’API dans une seule fonction Node.js 22 (functions/api.func, empaquetée avec esbuild ; dépendances tracées par @vercel/nft, polices PDF ajoutées explicitement).
  • Routage : en-têtes de sécurité du site, fichiers statiques, /api/* → fonction, tout le reste → index.html.
  • Le dossier de l’API s’appelle server/ et non api/ : Vercel transformerait chaque fichier d’un dossier api/ en fonction séparée.
  • Limites de la plateforme : 4,5 Mo par requête (d’où la compression des photos), 60 s par appel (maxDuration).
  • Tâche planifiée : /api/v1/cron/maintenance chaque jour à 5 h 15 UTC (fréquence compatible avec l’offre gratuite de Vercel). Vercel envoie automatiquement CRON_SECRET.

6.6Variante : serveur dédié

La même API fonctionne sur un serveur Ubuntu 24.04 avec Caddy (HTTPS) et systemd, grâce aux fichiers de deploy/. Base : la même base Supabase ou un PostgreSQL installé sur le serveur ; photos : Supabase Storage ou le disque (UPLOAD_DIR). Étapes principales :

$ apt install -y git curl caddy build-essential postgresql-client ufw
$ curl -fsSL https://deb.nodesource.com/setup_22.x | bash - && apt install -y nodejs
$ ufw allow OpenSSH && ufw allow 80,443/tcp && ufw enable
$ useradd --system --home-dir /var/lib/kader-cargo --shell /usr/sbin/nologin kader
$ mkdir -p /var/lib/kader-cargo/uploads && chown -R kader:kader /var/lib/kader-cargo
$ git clone git@github.com:siaoctawacta/Tracking.git /srv/kader-cargo     # clé de déploiement
$ cd /srv/kader-cargo && cp deploy/env.production.example server/.env && nano server/.env
$ chown root:kader server/.env && chmod 640 server/.env
$ npm --prefix server ci && npm --prefix web ci && npm --prefix web run build
$ cd server && runuser -u kader -- ./node_modules/.bin/prisma migrate deploy
$ runuser -u kader -- npm run create-admin -- --name "Kader" --email admin@kadercargo.com
$ cp ../deploy/kader-cargo-api.service /etc/systemd/system/ && systemctl daemon-reload && systemctl enable --now kader-cargo-api
$ cp ../deploy/Caddyfile /etc/caddy/Caddyfile && nano /etc/caddy/Caddyfile && systemctl reload caddy
$ cp ../deploy/cron.kader-cargo /etc/cron.d/kader-cargo

Le service systemd est isolé (systemd-analyze security : 2.9 OK) et ne peut écrire que dans /var/lib/kader-cargo. Mises à jour : deploy/update.sh ; sauvegardes nocturnes : deploy/backup.sh (pg_dump + photos locales).

07 / exploitation

Exploitation

Mises à jour, sauvegardes et restauration, surveillance, dépannage et mise en production.

deploy · backup · monitor

7.1Mettre à jour

Sur Vercel, chaque fusion sur main déclenche un déploiement de production : build du site et de la fonction, migrations de la base, mise en ligne sans interruption. En cas de problème, Instant Rollback (onglet Deployments) remet en ligne la version précédente — sans annuler une migration déjà appliquée : les migrations doivent donc rester compatibles avec la version précédente (ajouts plutôt que suppressions).

7.2Sauvegardes et restauration

  • Base : Supabase fait des sauvegardes selon votre offre (onglet Database → Backups). En complément, une copie indépendante, depuis n’importe quel ordinateur ayant le client PostgreSQL (version égale ou plus récente que celle de Supabase) :
$ DIRECT_URL="…Session pooler…" npm --prefix server run backup -- kader-2026-11-15.dump

# Restauration (remplace les tables par celles de la sauvegarde — testée)
$ pg_restore --clean --if-exists --no-owner --dbname "…Session pooler…" kader-2026-11-15.dump
  • Photos : elles sont dans le bucket photos, qui n’est pas inclus dans les sauvegardes de la base. Téléchargez-le régulièrement (outils de Supabase ou tout outil compatible S3) si ces photos ont valeur de preuve.
  • Restauration : les données reviennent à l’état de la sauvegarde ; ce qui a été saisi après est perdu.

7.3Surveillance et dépannage

Journaux : Vercel → projet → Logs (appels de la fonction, alertes WhatsApp, erreurs) ; Supabase → Logs (base, Storage). Surveillez /api/v1/health avec un service externe (UptimeRobot, Better Stack…).

SymptômeCause probable et action

7.4Check-list de mise en production

  • JWT_SECRET et CRON_SECRET uniques ; clé service_role uniquement dans les variables Vercel.
  • Bucket photos privé ; SSL vérifié (DATABASE_SSL=verify) recommandé.
  • Variables de base absentes de l’environnement Preview (ou second projet Supabase).
  • WhatsApp et SMTP configurés et testés avant d’ouvrir les inscriptions ; modèles approuvés.
  • PUBLIC_WEB_URL à jour après l’ajout du domaine.
  • Sauvegarde indépendante (pg_dump) planifiée et une restauration testée ; copie du bucket photos.
  • Un compte nominatif par employé ; désactivation au départ. Supervision de /api/v1/health.
