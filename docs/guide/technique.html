1.1Vue d’ensemble

L’application est découplée : une application monopage (SPA) React servie comme fichiers statiques, et une API REST JSON sans état en Node.js. Elles ne communiquent que par HTTPS, sous /api/v1. L’API ne génère aucun HTML ; la SPA ne contient aucune logique métier (prix, numéros de suivi, transitions de statut et droits sont décidés par l’API).

1.5Cycle de vie d’un colis et droits

Statuts ordonnés : REGISTERED → LOADING → IN_TRANSIT → ARRIVED → READY → DELIVERED. Chaque changement crée un ShipmentEvent et, s’il fait avancer le colis, une alerte WhatsApp pour l’étape.

RôleStatuts autorisésRègle
AGENT_GZREGISTERED, LOADING, IN_TRANSITUniquement vers l’avant (sinon 409 status_backwards)
AGENT_LOMEARRIVED, READY, DELIVERED
ADMINTousPeut corriger en arrière : aucune alerte n’est alors envoyée
CLIENTAucunLecture de ses propres colis uniquement

Numéro de suivi : KC-AAAA-XXXXXX, 6 caractères tirés par générateur cryptographique dans un alphabet de 32 signes sans 0/O ni 1/I (plus d’un milliard de combinaisons). Prix calculé par l’API : aérien au kg, maritime au m³, minimum de facturation (server/src/lib/domain.ts).

2.4Conventions

  • Toute modification du modèle passe par une migration (db:migrate) versionnée dans server/prisma/migrations/. Après une migration, régénérer le client : npx prisma generate (fait automatiquement par npm install).
  • Chaque entrée de l’API est décrite par un schéma zod .strict() : un champ inconnu est refusé (400 validation_error).
  • Les erreurs métier passent par HttpError(statut, message, code) ; les messages sont en français, destinés à l’utilisateur.
  • Les coordonnées affichées sont dans web/src/lib/site.ts, celles des messages et PDF dans server/src/lib/company.ts, les tarifs dans server/src/lib/domain.ts.

Format

3.2Exemple de session

# 1. Jeton CSRF (renvoyé dans le corps + cookie HttpOnly)
$ curl -c jar https://kadercargo.com/api/v1/auth/csrf

# 2. Connexion : pose les cookies de session
$ curl -b jar -c jar -H "X-CSRF-Token: V3hF…" -H "Content-Type: application/json" \

{"user":{"id":"cm…","name":"Kader","email":"admin@kadercargo.com","phone":null,"role":"ADMIN"}}

# 3. Lecture (GET : pas de jeton CSRF)
$ curl -b jar "https://kadercargo.com/api/v1/shipments?status=IN_TRANSIT&mode=AIR"

# 4. Session expirée (401) : rotation silencieuse puis nouvel essai
$ curl -b jar -c jar -X POST -H "X-CSRF-Token: V3hF…" https://kadercargo.com/api/v1/auth/refresh

04 / sécurité

Sécurité de l’application

Mots de passe, sessions, codes de vérification, contrôle d’accès, entrées, fichiers, en-têtes et limites connues.

OWASP Top 10

4.1Mots de passe

  • Hachage Argon2id (m=65536 Kio, t=3, p=1, sortie 32 octets) avec un sel aléatoire de 16 octets par hachage ; jamais stockés ni journalisés en clair.
  • Vérification à temps quasi constant : si l’utilisateur n’existe pas, un hachage factice est vérifié quand même ; le message d’erreur est identique (invalid_credentials).
  • Longueur minimale 10 caractères ; formulaires en type="password" avec autocomplete approprié.

4.2Sessions

ÉlémentMise en œuvre
Jeton d’accèsJWT HS256, 15 minutes, émetteur kader-cargo, audience kader-cargo-web, identifiant unique (jti) ; contient sub, role, name. L’API est sans état : chaque requête est authentifiée par ce jeton.
Refresh token32 octets aléatoires, 7 jours, stocké uniquement haché (SHA-256). Rotation à chaque usage ; un jeton déjà utilisé et rejoué révoque toute sa famille (détection de vol).
Cookies__Host-jwt, __Host-rt, __Host-csrf : HttpOnly; Secure; SameSite=Strict; Path=/, sans domaine. Inaccessibles au JavaScript (pas de localStorage).
Fin de sessionDéconnexion, désactivation ou refus d’un compte : révocation des refresh tokens en base.
SecretJWT_SECRET obligatoire en production (≥ 32 caractères) : l’API refuse de démarrer sinon.

4.3Protection CSRF et CORS

En plus de SameSite=Strict, toute requête qui modifie des données doit présenter dans l’en-tête X-CSRF-Token la même valeur que le cookie __Host-csrf (comparaison à temps constant). Le jeton est donné dans le corps de GET /auth/csrf, ce qui fonctionne aussi si le site et l’API sont sur des origines différentes. CORS n’est activé que si CORS_ORIGINS est renseigné (origines explicites, credentials, méthodes GET/POST/PATCH/DELETE).

4.4Codes de vérification et inscription

  • 6 chiffres tirés par crypto.randomInt. Seul un HMAC-SHA256 (clé : JWT_SECRET, message : destinataire + code) est stocké.
  • Validité 10 minutes, 5 essais puis verrouillage ; 60 s entre deux envois, 5 codes par heure et par destinataire ; un nouveau code invalide le précédent ; consommation atomique (un code ne sert qu’une fois).
  • Pas d’énumération des clients : une inscription sur un numéro existant envoie un code de connexion et répond exactement comme une nouvelle inscription ; une demande de code pour un compte inconnu répond pareil sans rien envoyer.
  • Un téléphone ou un e-mail n’est enregistré sur un compte qu’après preuve (code, Google, ou création par le personnel), car il donne accès aux colis enregistrés à ce numéro.
  • Comptes auto-inscrits en PENDING : aucune session possible (mot de passe, code, Google, refresh) avant validation par un administrateur.

4.5Connexion Google

Le jeton d’identité Google est vérifié par l’API (bibliothèque jose) : signature contre les clés publiques de Google, audience = GOOGLE_CLIENT_ID, émetteur accounts.google.com, expiration. Un compte existant n’est lié automatiquement que si Google certifie l’adresse (email_verified).

4.6Contrôle d’accès

  • Par rôle sur chaque route (middleware requireRole) et par statut (tableau 1.5).
  • Par objet : un client n’accède qu’aux colis dont le téléphone ou l’e-mail correspond à son compte ; sinon l’API répond 404 (et non 403) pour ne pas révéler l’existence du colis.
  • Le site masque les boutons non autorisés, mais l’API reste la seule autorité.
  • Suivi public : nom réduit (« Afi M. »), téléphone masqué (« +228 •• •• 33 ») ; 30 requêtes par minute et par IP contre l’énumération des numéros.

4.7Entrées, fichiers et erreurs

  • Injection SQL : uniquement des requêtes Prisma paramétrées, aucune requête SQL construite à la main.
  • Validation : schémas zod .strict() sur tous les corps et paramètres ; JSON limité à 100 Ko.
  • Photos : JPEG / PNG / WebP uniquement, vérifiés par signature binaire (le type annoncé par le navigateur ne suffit pas) ; 5 Mo, 8 fichiers ; nom aléatoire (UUID), droits 600, servies après contrôle d’accès avec X-Content-Type-Options: nosniff.
  • XSS : React échappe tout le contenu ; aucune insertion de HTML brut ; CSP stricte sur le site.
  • Erreurs : aucune trace technique renvoyée au client (détails seulement dans le journal).

4.8En-têtes HTTP

RéponseEn-têtes
API (helmet)Content-Security-Policy: default-src 'none'; frame-ancestors 'none', Strict-Transport-Security (2 ans, preload), X-Frame-Options: DENY, Referrer-Policy: no-referrer, Cross-Origin-Resource-Policy: same-site, pas de X-Powered-By.
Site (Caddy)CSP default-src 'self' (scripts, styles et polices du site uniquement ; exceptions limitées à accounts.google.com/gsi), HSTS, X-Frame-Options: DENY, nosniff, Permissions-Policy. Le thème est appliqué par un script externe (theme-init.js) pour éviter tout script en ligne.

4.9Limitation de débit

RoutesLimite (par adresse IP)
POST /auth/login5 par 15 minutes (LOGIN_RATE_LIMIT)
Inscription, codes, Google60 par 15 minutes (beaucoup de clients mobiles partagent une même IP d’opérateur) + limites par destinataire (4.4)

Derrière Caddy, TRUST_PROXY=1 est indispensable pour que l’IP réelle du client soit utilisée.

4.10Limites connues et recommandations

  • Une seule instance : les compteurs de limitation sont en mémoire et la base est un fichier SQLite. Pour plusieurs serveurs : PostgreSQL (fournisseur Prisma + adaptateur @prisma/adapter-pg, nouvelles migrations) et un stockage partagé des compteurs.
  • Sans WhatsApp ni SMTP configurés, les codes sont écrits dans le journal du serveur (mode « simulé ») : configurer les fournisseurs avant d’ouvrir les inscriptions.
  • Pas de double authentification pour le personnel : recommandé si l’équipe grandit (un code par e-mail à chaque connexion, par exemple).
  • Les codes et jetons expirés restent en base : une purge périodique est recommandée à terme (tables OtpCode, RefreshToken).
  • Les notifications du back-office sont lues par interrogation toutes les 10 secondes (simple et compatible avec une API sans état).
05 / intégrations

Intégrations

WhatsApp, e-mail et connexion Google : fonctionnement et configuration.

twilio · meta · smtp · google

5.1WhatsApp

Code : server/src/lib/whatsapp.ts. Fournisseur choisi par WHATSAPP_PROVIDER ou détecté selon les identifiants présents ; sans identifiants : mode simulé.

  • Alertes d’étape : un message par étape franchie vers l’avant (y compris en masse), au plus un par étape et par colis ; envoi en arrière-plan, 3 tentatives (immédiate, +30 s, +2 min) ; après le dernier échec, notification WHATSAPP_FAILED aux administrateurs.
  • Codes et avis de compte : envoi immédiat (la réponse HTTP attend le résultat).
  • Meta : modèles approuvés nommés {META_TEMPLATE_PREFIX}{étape}, variables du corps {{1}} prénom, {{2}} numéro de suivi, {{3}} détail ; le modèle kader_otp (catégorie Authentification) porte aussi le code dans son bouton « Copier ».
  • Twilio : texte libre, ou modèles Content si TWILIO_CONTENT_SIDS associe une étape à un identifiant HX….
ModèleCatégorieUsage
kader_registered … kader_deliveredUtility6 alertes d’étape (registered, loading, in_transit, arrived, ready, delivered)
kader_otpAuthentificationCode de vérification
kader_accountUtilityCompte validé / refusé

Les textes à soumettre à Meta ou Twilio sont dans docs/whatsapp-alertes.md.

5.2E-mail

Code : server/src/lib/mailer.ts (nodemailer, SMTP). Avec Gmail : validation en deux étapes, puis un mot de passe d’application dans SMTP_PASS, SMTP_HOST=smtp.gmail.com, port 465 sécurisé. Gmail limite le volume quotidien ; pour un volume plus important, utiliser un service d’envoi dédié (mêmes variables SMTP). Les e-mails sont envoyés en texte et en HTML aux couleurs de Kader Cargo.

5.3Connexion Google

  1. console.cloud.google.com : créer un projet, configurer l’écran de consentement OAuth (nom, logo, e-mail d’assistance).
  2. Identifiants → ID client OAuth, type « Application Web », origine JavaScript autorisée : https://kadercargo.com.
  3. Renseigner GOOGLE_CLIENT_ID et redémarrer l’API. Le site le récupère via GET /auth/options : aucune reconstruction du site n’est nécessaire.

6.4Variante : site sur Vercel, API sur le serveur

Vercel peut héberger le site, mais pas l’API : ses fonctions sont éphémères, la base SQLite et les photos y seraient perdues. Dans cette variante, l’API est installée sur le serveur comme ci-dessus (étapes 1 à 10) sous un sous-domaine, par exemple api.kadercargo.com dans le Caddyfile, et Vercel lui transmet les appels /api/*. Le site et l’API restent ainsi sur la même adresse, ce qu’exigent les cookies de session SameSite=Strict.

FichierRôle
vercel.jsonInstalle et construit uniquement web/, publie web/dist, transmet /api/* à l’API, renvoie les autres adresses vers index.html, ajoute les en-têtes de sécurité du site.
.vercelignoreExclut api/, deploy/, docs/, brand/ : sans lui, Vercel prendrait le dossier api/ pour des fonctions serverless et le build échouerait.
  1. Dans vercel.json, remplacez https://api.kadercargo.com par l’adresse réelle de l’API, puis publiez sur main.
  2. Dans Vercel : Root Directory = racine du dépôt (laisser vide), aucun réglage de build à saisir (tout est dans vercel.json), domaine personnalisé kadercargo.com.
  3. Sur le serveur, dans server/.env : TRUST_PROXY=2 (Vercel puis Caddy) et PUBLIC_WEB_URL = l’adresse du site sur Vercel ; redémarrez l’API.
  4. Vérifiez https://kadercargo.com/api/v1/health, une connexion, puis l’envoi d’une photo de contrôle.
Points d’attention

Avec TRUST_PROXY=1, tous les visiteurs auraient l’adresse IP de Vercel et partageraient la limite de 5 essais de connexion. Avec TRUST_PROXY=2, quelqu’un qui appelle directement api.kadercargo.com pourrait fausser son adresse IP pour contourner cette limite : gardez des mots de passe robustes. Vérifiez aussi que l’envoi des photos (jusqu’à 5 Mo chacune) passe par le relais de Vercel. Si ces contraintes gênent, la solution la plus simple reste d’héberger site et API sur le même serveur avec Caddy (6.2).

Exploitation

Mises à jour, sauvegardes et restauration, surveillance, dépannage et mise en production.

run · backup · monitor

7.1Mettre à jour

$ /srv/kader-cargo/deploy/update.sh

Enchaîne : sauvegarde → git pull --ff-only origin main → npm ci (api, web) → prisma migrate deploy (sans perte de données) → build du site → redémarrage → vérification de /api/v1/health pendant 20 s. En cas d’échec, il l’indique avec la commande du journal à consulter.

7.2Sauvegardes et restauration

backup.sh (chaque nuit à 2 h 30) crée dans /var/backups/kader-cargo une copie cohérente de la base faite pendant le fonctionnement (API de sauvegarde SQLite) et une archive des photos, puis supprime ce qui a plus de 14 jours.

Copie hors serveur

Copiez régulièrement ce dossier ailleurs (stockage cloud, autre serveur — par exemple avec rclone ou scp) et activez si possible les instantanés de votre hébergeur.

# Restauration (testée)
$ systemctl stop kader-cargo-api
$ cp /var/lib/kader-cargo/kader.db /var/lib/kader-cargo/kader.db.avant-restauration
$ cp /var/backups/kader-cargo/kader-AAAA-MM-JJ_HHMM.db /var/lib/kader-cargo/kader.db
$ rm -f /var/lib/kader-cargo/kader.db-wal /var/lib/kader-cargo/kader.db-shm
$ tar -xzf /var/backups/kader-cargo/photos-AAAA-MM-JJ_HHMM.tar.gz -C /var/lib/kader-cargo
$ chown -R kader:kader /var/lib/kader-cargo
$ systemctl start kader-cargo-api

Les données reviennent à l’état du moment de la sauvegarde.

7.3Surveillance et dépannage

$ systemctl status kader-cargo-api      # état
$ journalctl -u kader-cargo-api -f      # journal en direct
$ journalctl -u caddy -n 50             # HTTPS
$ curl https://kadercargo.com/api/v1/health

Surveillez /api/v1/health avec un service externe (UptimeRobot, Better Stack…) pour être alerté d’une panne.

SymptômeCause probable et action
Site inaccessibleDNS, pare-feu (ufw status), systemctl status caddy.
502 Bad GatewayAPI arrêtée : lire le journal, puis systemctl restart kader-cargo-api.
« JWT_SECRET must be set… »Secret absent ou trop court dans server/.env.
Alertes « Simulé »Aucun fournisseur WhatsApp configuré.
Alertes « Échec »Identifiants, modèles non approuvés ou numéro invalide : message d’erreur dans la fiche du colis et dans le journal.

7.4Check-list de mise en production

  • NODE_ENV=production, JWT_SECRET unique et secret, server/.env en 640 (root:kader).
  • SSH par clé uniquement, mot de passe root désactivé, unattended-upgrades actif, pare-feu limité à SSH/80/443.
  • WhatsApp et SMTP configurés et testés avant d’ouvrir les inscriptions ; modèles approuvés.
  • PUBLIC_WEB_URL et TRUST_PROXY=1 renseignés.
  • Sauvegarde nocturne active, copiée hors serveur, restauration testée.
  • Un compte nominatif par employé ; désactivation au départ.
  • Supervision externe de /api/v1/health.
